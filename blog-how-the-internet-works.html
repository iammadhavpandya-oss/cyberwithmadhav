How the Internet Works: From Typing a URL to Seeing a Page

You open a website dozens of times a day. Understanding what happens in those few hundred milliseconds is one of the best foundations for a career in security.

Quick answer

When you type a website address, your device asks DNS for the server's IP address, opens a TCP connection to it, sets up encryption with TLS (the padlock in HTTPS), and then sends an HTTP request. The server sends back HTML, images and scripts, and your browser builds the page. Each step has its own security risks and protections.

Step 1: Finding the address with DNS

You type www.example.com. Your computer does not know where that is, so it asks a DNS resolver, usually run by your internet provider or a public service. The resolver finds the IP address and replies. Your device caches the answer for a while so the next visit is faster.

Security angle: attackers register lookalike domains, for example swapping one letter, to fool people. Some malware also tampers with DNS settings to send you to fake sites. This is why you should always read the domain name carefully, especially for banking. Indian banks now use the .bank.in ending, explained in this guide.

Step 2: Routing packets across networks

With the IP address known, your device sends data in small chunks called packets. They go to your home router, then your internet provider, then across many routers until they reach the server's network. Each router just looks at the destination IP and forwards the packet closer.

Security angle: anyone who controls a network on the path, such as a fake public WiFi hotspot, could try to see or modify unencrypted traffic. This is the reason encryption matters so much.

Step 3: Opening a TCP connection

Web traffic uses TCP, which makes sure data arrives complete and in order. Before sending real data, client and server do a quick greeting called the three way handshake: SYN, SYN-ACK, ACK. After that, the connection is open on the server's port, usually 443 for HTTPS.

Security angle: port scanners like nmap use this handshake behaviour to discover which ports are open. Defenders watch for many half finished handshakes, which can signal scanning or a flood attack.

Step 4: TLS, the padlock

For HTTPS, the browser and server now set up TLS encryption. The server shows a certificate that proves it controls that domain name, signed by a trusted certificate authority. They agree on keys, and from here everything is encrypted.

Security angle, very important: the padlock means the connection is encrypted and the domain matches the certificate. It does not mean the website is genuine or safe. Phishing sites also get free certificates. A padlock on sbi-kyc-update-help.com is still a scam site. Teach this to your family.

Step 5: HTTP request and response

Inside the encrypted tunnel, your browser sends an HTTP request, like GET /index.html, along with headers such as cookies. The server replies with a status code (200 OK, 404 Not Found, 500 Server Error) and the content. Your browser then fetches more files for images, styles and scripts, and builds the page you see.

Security angle: cookies often hold your logged in session. If an attacker steals that cookie, they may not need your password. Web attacks such as cross site scripting and SQL injection happen at this layer. You will learn them on practice sites in the Burp Suite intro.

See it yourself in five minutes

  1. Open any website in Chrome or Firefox.
  2. Press F12 to open developer tools and click the Network tab.
  3. Reload the page. You will see every request, its status code, size and timing.
  4. Click the padlock in the address bar and view the certificate details.
  5. In a terminal, run nslookup example.com to see the DNS step on its own.

This is all on your own browser, so it is completely safe. Once you can explain these five steps to a friend in simple Hindi or English, you have a stronger foundation than many people who only know tool names. Part 6 maps these steps to the OSI and TCP/IP models.

Frequently asked questions

Is HTTPS enough to keep me safe? HTTPS protects data in transit from people on the network. It does not protect you from a fake website, a malicious download or a scammer on the phone. Always combine it with checking the domain and thinking before you share details.

What is a VPN in this picture? A VPN wraps your traffic in another encrypted tunnel to the VPN provider, who then sends it to the website. It changes who can see your traffic, it does not make every site safe. Our VPN myths post explains more.

Why do some sites load slowly? Every step adds time: DNS lookup, distance to the server, TLS setup and many files. Developer tools show which step is slow, a skill that is also useful in troubleshooting jobs.

Key takeaways

  • A web visit is DNS lookup, TCP connection, TLS handshake, then HTTP request and response.
  • HTTPS encrypts traffic, but a padlock does not prove a site is honest.
  • Phishing abuses the DNS and domain step, so always read the real domain name.
  • Browser developer tools let you watch all of this on your own machine.
